\section{DevOps Overview}
\subsection*{What and Why}
DevOps is the practice of combining software development and operations so that product increments can reach users quickly and safely. For this project, DevOps bridges the scientific calculator codebase and the deployment host: every change moves from Git commits through automated tests, container builds, image pushes, and finally to an Ansible-managed runtime. Automating these feedback loops reduces manual effort, ensures reproducibility, and keeps the calculator available.

\subsection*{Toolchain Summary}
\begin{itemize}[leftmargin=*]
  \item \textbf{GitHub} --- central source control for the repository (\href{https://github.com/pradyunuydarp/CI-CD-Learning}{CI-CD-Learning}) and pull-request history.
  \item \textbf{Node.js 20 \& Next.js 15} --- application runtime and framework powering the web UI.
  \item \textbf{TypeScript \& ESLint} --- static typing and linting to catch issues before runtime.
  \item \textbf{Vitest} --- unit testing harness for the calculator logic.
  \item \textbf{Jenkins} --- orchestrates the CI pipeline across install, test, build, container, and deploy stages.
  \item \textbf{Docker} --- packages the Next.js application into a portable image.
  \item \textbf{Docker Hub} --- hosts the pushed image under \href{https://hub.docker.com/r/pradyunuydarp/sci-calc-next}{pradyunuydarp/sci-calc-next}.
  \item \textbf{Ansible} --- pulls the published image and manages the running container on the deployment target.
  \item \textbf{Ansible Vault} --- stores Docker Hub credentials for production pulls.
  \item \textbf{LaTeX} --- renders this report as a PDF artefact for submission.
\end{itemize}

\section{System Architecture}
\begin{itemize}[leftmargin=*]
  \item Next.js App Router renders the UI under \texttt{src/app}. The main calculator form is implemented in \texttt{src/components/Calculator.tsx} and rendered by \texttt{src/app/page.tsx}.
  \item Computations live in \texttt{src/lib/math.ts} with exported helpers \texttt{sqrtX}, \texttt{factX}, \texttt{lnX}, and \texttt{power}. Input validation guards edge cases (negative factorials, non-positive logarithm operands, etc.).
  \item API requests hit \texttt{src/app/api/calc/route.ts}, which accepts JSON payloads, validates the requested operation, and delegates to the math helpers.
  \item Styling relies on utility classes to keep the layout responsive across laptops and tablets.
\end{itemize}

\section{Implementation Walkthrough}
\subsection{Source Control Management (GitHub)}
The project lives at \href{https://github.com/pradyunuydarp/CI-CD-Learning}{github.com/pradyunuydarp/CI-CD-Learning}. The \texttt{sci-calc-next} directory is the Next.js workspace. Typical commands:
\begin{verbatim}
# clone
$ git clone https://github.com/pradyunuydarp/CI-CD-Learning.git
$ cd CI-CD-Learning/sci-calc-next

# create feature branch, then commit
$ git checkout -b feat/new-capability
$ git add src/app/page.tsx
$ git commit -m "feat(ui): surface factorial operation"
$ git push origin feat/new-capability
\end{verbatim}
Jenkins tracks the \texttt{main} branch via a GitHub webhook, so every push schedules a pipeline run automatically.

\subsection{Testing and Quality Gates}
Unit tests use Vitest and live in \texttt{src/lib/math.test.ts}. Linting enforces Next.js conventions. Both run locally and in CI:
\begin{verbatim}
$ npm run lint
$ npm run test
\end{verbatim}
The pipeline stops if either command fails, preventing regressions from reaching Docker build or deployment stages.

\subsection{Build Automation}
The production bundle is created with the standard Next.js build command:
\begin{verbatim}
$ npm run build
\end{verbatim}
In Jenkins, the build stage sets \texttt{NODE\_ENV=production} inline for the command so that devDependencies remain available during earlier steps.

\subsection{Continuous Integration with Jenkins}
The Jenkinsfile orchestrates every step. The Install stage now clears leftover dependencies to avoid \texttt{ENOTEMPTY} errors before running \texttt{npm ci}. Relevant excerpt:
\begin{verbatim}
stage('Install') {
  steps {
    dir('sci-calc-next') {
      sh 'node -v'
      sh 'rm -rf node_modules'
      sh 'npm ci'
    }
  }
}
\end{verbatim}

Dynamic host-port detection prevents deploy clashes, and email notifications keep the team informed. The success/failure handlers share build metadata, Docker tag, and the resolved host port:
\begin{verbatim}
post {
  success {
    script {
      if (env.NOTIFY_EMAILS?.trim()) {
        emailext(
          to: env.NOTIFY_EMAILS,
          subject: "SciCalc Next build #${env.BUILD_NUMBER} succeeded",
          mimeType: 'text/html',
          body: """
<p>Build <a href='${env.BUILD_URL}'>#${env.BUILD_NUMBER}</a> completed successfully.</p>
<p>Docker image: ${env.DOCKER_IMAGE ?: 'n/a'}<br/>
Host port: ${env.DEPLOY_HOST_PORT ?: '3000'}</p>
"""
        )
      }
    }
  }
  failure {
    echo 'Pipeline failed. Review the logs for details.'
    script {
      if (env.NOTIFY_EMAILS?.trim()) {
        emailext(
          to: env.NOTIFY_EMAILS,
          subject: "SciCalc Next build #${env.BUILD_NUMBER} failed",
          mimeType: 'text/html',
          body: """
<p>Build <a href='${env.BUILD_URL}'>#${env.BUILD_NUMBER}</a> failed.</p>
<p>Review the <a href='${env.BUILD_URL}console'>console log</a> for details.</p>
""",
          attachLog: true
        )
      }
    }
  }
}
\end{verbatim}
During the 10~Oct~2025 run at 16:34 the script detected that port~3000 was occupied, selected 3300 automatically, and completed deployment without manual intervention.

\subsection{Containerization}
The Dockerfile performs a multi-stage build. Key fragment:
\begin{verbatim}
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
ENV NODE\_ENV=production
WORKDIR /app
COPY --from=builder /app/package*.json ./
COPY --from=builder /app/.next ./.next
COPY --from=builder /app/public ./public
RUN npm ci --omit=dev
EXPOSE 3000
CMD ["npm", "run", "start"]
\end{verbatim}
The Jenkins Docker stage logs into Docker Hub using the \texttt{dockerhub} credential and tags the image as \texttt{pradyunuydarp/sci-calc-next:latest}.

\subsection{Registry Publishing}
Image publishing relies on native Docker CLI commands executed from Jenkins:
\begin{verbatim}
echo "${DOCKERHUB_TOKEN}" | docker login -u "${DOCKERHUB_USER}" --password-stdin
docker build -t "${DOCKERHUB_USER}/sci-calc-next:latest" .
docker push "${DOCKERHUB_USER}/sci-calc-next:latest"
docker logout
\end{verbatim}
The resulting image is visible under \href{https://hub.docker.com/r/pradyunuydarp/sci-calc-next/tags}{Docker Hub tags}.

\subsection{Configuration Management and Deployment}
Ansible handles the final delivery. Inventory and group variables pin the container name, port mapping, and interpreter:
\begin{verbatim}
# ansible/inventory/hosts.ini
[targets]
localhost ansible_connection=local

# ansible/inventory/group_vars/all.yml
app_name: sci-calc-next
docker_image: "{{ lookup('env', 'DOCKER_IMAGE') | default('pradyunuydarp/sci-calc-next:latest', true) }}"
container_name: sci-calc-next
container_port: 3000
host_port: "{{ lookup('env', 'HOST_PORT') | default('3000', true) }}"
ansible_python_interpreter: "{{ lookup('env', 'ANSIBLE_PYTHON_INTERPRETER') | default('/usr/bin/env python3', true) }}"
\end{verbatim}

The deploy playbook removes stale containers, pulls the requested image, and recreates the service:
\begin{verbatim}
- name: Stop existing SciCalc Next container
  community.docker.docker_container:
    name: "{{ container_name }}"
    state: stopped
  ignore_errors: true

- name: Remove existing SciCalc Next container
  community.docker.docker_container:
    name: "{{ container_name }}"
    state: absent
  ignore_errors: true

- name: Ensure SciCalc Next container is running
  community.docker.docker_container:
    name: "{{ container_name }}"
    image: "{{ docker_image }}"
    state: started
    recreate: true
    force_kill: true
    restart_policy: always
    published_ports:
      - "{{ host_port }}:{{ container_port }}"
    env:
      NODE_ENV: production
\end{verbatim}
During the successful Jenkins run, the play recap reported \texttt{ok=3 changed=1 failed=0}, confirming the container restart on the new port.

\section{Application Experience}
\subsection*{User Journey}
Landing on \texttt{/} presents a centered glassmorphism shell with the "SciCalc Next" banner and a two-column layout on desktop. The left pane hosts the interactive form: four quick-action pills switch between square root, factorial, natural logarithm, and power, while an optional free-form expression box accepts inputs such as \texttt{5!}, \texttt{sqrt(144)}, \texttt{ln(10)}, or \texttt{pow(2,8)}. Selecting an operation swaps in the relevant structured fields (single numeric input for unary functions, paired base/exponent inputs for power) so the user can either type shorthand math or rely on labelled controls.

\subsection*{Feedback Loop}
Submitting the form issues a \texttt{POST} to \texttt{/api/calc}, which validates the payload and runs the math helpers. Results appear instantly in the right-hand "Result preview" card, formatted with up to six decimal places and wrapped in a scrollable badge for long outputs. A single click copies the numeric answer to the clipboard and surfaces a transient "Copied!" indicator; unsupported clipboard environments fall back to an inline warning instead of failing silently.

\subsection*{Guidance and Validation}
Each operation tile advertises its domain (e.g., factorial highlights non-negative integers, logarithm warns about positive inputs only), and the sidebar mirrors the currently selected operation with a description and worked example. Client-side parsing catches malformed expressions before the request leaves the browser, while the API raises explicit error messages for domain breaches such as negative square roots or overflowing factorials. These messages render in the sidebar with accentuated error styling, ensuring users understand why a computation failed.

\subsection*{Responsiveness and Accessibility}
The grid collapses to a single column below 960~px, keeping the keypad, inputs, and feedback stacked for mobile reachability. Buttons expose \texttt{aria-pressed} state, results live in an \texttt{aria-live} region, and focus-visible styles ensure keyboard navigation remains clear. Color contrast between foreground text and the dark background exceeds WCAG~AA targets, making the calculator legible in low-light settings.
\section{Runtime Access}
A secure tunnel is exposed through ngrok during local demos so remote reviewers can reach the calculator without opening firewall ports.

\section{Appendix A: Assignment Brief}
\subsection*{Problem Statement}
Create a scientific calculator that supports the following operations: square root (\(\sqrt{x}\)), factorial (\(x!\)), natural logarithm (\(\ln x\)), and exponentiation (\(x^b\)). The solution may be a command-line or web application in any programming language.

\subsection*{DevOps Requirements}
\begin{enumerate}[leftmargin=*]
  \item Manage the source code with Git on a hosted platform such as GitHub, GitLab, or Bitbucket.
  \item Implement automated testing (JUnit, Selenium, Vitest, etc.).
  \item Configure a build step using tools like Maven, Gradle, npm, or equivalents.
  \item Set up continuous integration with Jenkins.
  \item Containerise the application with Docker.
  \item Push the resulting image to Docker Hub.
  \item Use Ansible for configuration management: pull the image to managed hosts and run the container (local machine or cloud host).
  \item Document the entire pipeline and provide screenshots demonstrating each stage and calculator functionality.
\end{enumerate}

\subsection*{Submission Expectations}
\begin{itemize}[leftmargin=*]
  \item Report on the DevOps approach, tools, configuration steps, commands, and screenshots of key milestones (Git commits, Jenkins credentials, Docker Hub repository, Ansible execution, and application UI).
  \item Provide artefacts such as the Dockerfile, Ansible playbooks, Jenkinsfile, and application source code.
  \item Include links to the public GitHub repository and Docker Hub image in the report.
  \item Export the final document as PDF named with the roll number.
\end{itemize}

\section{Learnings and Improvements}
\begin{itemize}[leftmargin=*]
  \item Automated port detection in Jenkins prevented repeated binding errors once multiple containers were active on the same host.
  \item Exporting the virtual environment interpreter resolved ``module not found'' issues for \texttt{community.docker} modules.
  \item Future enhancements include Playwright smoke tests, caching the Ansible virtual environment between Jenkins runs, and promoting tagged releases through a staging environment before production.
\end{itemize}
